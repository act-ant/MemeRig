# MemeRig 多会话多任务执行计划

状态：规划评审。任务 ID：`08657309-3d96-4073-9f1a-36f1949225d8`。

## 1. 目标与范围

让同一仓库中的多个 Agent 会话同时推进不同任务。每次执行有独立代码工作区和可追溯结果。实现会话退出后，审查者可以凭持久记录接手，从审查、交付走到关闭。

MemeRig 已有会话级当前任务指针、`task.json` v1、任务存储写锁、原子替换和版本检查。首版复用这些能力，交付同机多进程执行、同任务领取互斥、退出回填、审查和落地确认。用户显式选择要运行的任务。跨机器队列、自动依赖调度、外部看板和 PR 事件自动关单作为独立接入项。

## 2. 数据与存储

| 记录 | 位置与字段 | 写入权与生命周期 |
| --- | --- | --- |
| Task | `tasks/<slug>/task.json`。沿用 `id`、`schemaVersion`、`status`、`parentId`、`nextAction` 等 v1 字段。受管执行通过 MemeRig 命名空间保存当前候选 `runId` 以及关闭所引用的交付记录 | Python 生命周期写入层更新，需求和验收标准放在同目录 `prd.md` |
| Session binding | `.runtime/sessions/<context-key>.json`。关联 `taskId`、`runId`、角色与当前任务上下文 | 会话切换时更新，退出时按原绑定清理，避免迟到 Hook 清掉新的关联 |
| Claim | `.runtime/` 下的任务领取记录。含 `taskId`、`runId`、`contextId`、`leaseExpiresAt` 和工作区引用 | 同一任务最多一个有效的实现领取，续租和结算核对当前 `runId`，租约结束可回收 |
| Run receipt v1 | `tasks/<slug>/runs/<runId>.json`。含 `taskId`、`runId`、起止时间、`outcome`、`sessions[]`、候选提交、产物和 `checks[]` | 启动器结算。以 `runId` 幂等写入，失败、中断及重跑分别保留 |
| Review receipt v1 | `tasks/<slug>/reviews/<reviewId>.json`。含 `taskId`、`runId`、审查者和可选 Session 引用、审查时间、被审查提交或产物版本、结论、验证和证据 | 审查流程写入。批准绑定具体候选和版本 |
| Delivery receipt v1 | `tasks/<slug>/deliveries/<deliveryId>.json`。关联 `taskId`、`runId`、通过的审查、交付位置、落地证据和时间。代码任务分别记录被审查的提交和实际落地提交 | 有权完成交付确认的入口写入。关闭任务前可重复核对和补记 |

路径均相对于 `.memerig/`。每个会话引用使用 `provider`、`ref`、`role`。实现与子会话共享同一次 `runId`，审查会话写入审查回执。历史归属以回执为准。子会话只继承任务上下文，领取和结算仍由运行器负责。会话引用可选，交接依赖可访问的提交、PR、仓库相对路径和验证证据。原始会话、完整日志、密钥、本机绝对路径及大产物留在宿主或专用存储。

回执使用版本化 JSON Schema 校验。运行时校验所有引用、合法状态迁移以及候选提交或产物版本匹配。检查结果区分 `passed`、`failed`、`not_run`，必跑项需要有可核对的通过证据。`parentId` 继续表达拆解关系，后续如有自动调度需求再定义 `dependsOn`。

## 3. 并发与恢复约束

1. **唯一任务存储。** 启动器把任务 owner、`taskId`、`runId` 显式传给受管执行，校验代码 worktree 与 owner 属于同一 Git 仓库，并兼容模块 `task_owner` 规则。所有状态和回执写入 owner。worktree 中的任务目录副本不得作为写入目标。
2. **短锁领取。** 在现有存储锁内检查任务与版本、修复未完成结算、校验有效领取，再写入新的领取记录。释放锁后创建专用 worktree 和分支，续租覆盖初始化与执行。不同任务的代码与测试可以同时运行。
3. **过期接手。** 失去领取的运行不再有续租、写回执或推进任务的权限。启动器观察到失去领取时停止受管子进程。重领使用新 `runId` 和新 worktree，旧 worktree 保留待检查。worktree 隔离 Git checkout，共用端口、外部服务和最终合并仍需各自协调。
4. **幂等结算。** 在同一锁内按「写终态回执 → 更新任务状态 → 释放运行领取」结算。新领取前根据已写回执补齐中断步骤。重复请求返回既有结果，冲突内容报错。先后校验当前领取及任务版本，拒绝迟到结果覆盖新候选。强杀或掉线时根据已持久化证据标注中断，未观察到的结果不得推断为成功。
5. **所有状态写入口遵守约束。** 受管任务的 `start`、`update`、`complete` 及回调统一调用生命周期写入层，防止会话绑定、重复通知或旧命令绕过领取、审查和交付。既有手工任务沿用当前命令行为。

## 4. 从接单到交付

| 步骤 | 行为与退出条件 |
| --- | --- |
| 规划 | 确定验收标准、必跑检查、交付位置及责任人。代码任务明确目标分支和合并要求 |
| 领取与执行 | 运行器领取、创建 worktree、绑定主会话及子会话，执行与核对产物 |
| 交接 | 运行器写入终态执行回执并释放领取。有效候选进入 `review`，失败与中断保留现场供再次执行 |
| 审查 | 以 `runId` 和提交或产物版本审查，补齐必跑验证。打回保留意见，返工开启新 `runId`。批准后候选仍可在 `review` 等落地 |
| 交付 | 按仓库规则合并 PR 或确认产物已进入指定位置。核对合并前的 PR head 与批准版本一致，squash 或 rebase 另外保存实际落地提交。文档与调研按约定路径及版本确认交付 |
| 关闭与归档 | 记录可核对的落地证据，确认当前候选已通过验收后再执行 `complete`。回填最终交付引用和关闭时间，保留原目录，从 `list --closed` 查询 |

若批准后候选版本变化，应重新审查。PR 创建和 Agent 退出均只产生阶段性证据。合并成功后若关闭写入中断，下一次交付核对依据仓库和 PR 证据补记，不重复合并。关闭后清理本次会话绑定及已结算运行时记录。回收 worktree 前确认无未提交改动、交付提交有持久引用，且没有运行仍在使用它。

**Git 管理。** Git 跟踪模式下，任务 owner checkout 管理任务文件和持久回执，执行 worktree 负责代码提交。代码合并和任务关闭可以分两次提交。`.runtime/`、锁与本机工作区信息保留本地。`tasks.version_control: local` 的项目继续使用同一协议，在本地留存任务文件。Git 可共享归档与证据，独立 clone 的实时领取需要独立协调层。

## 5. Hook 自动化

| 事件 | 动作 | 恢复或边界 |
| --- | --- | --- |
| `after_start` 或宿主会话启动 | 根据显式身份绑定任务和执行，注入 PRD 与验收上下文 | 身份缺失时不猜任务，受管入口给出错误 |
| 子会话启动 | 继承 `taskId`、`runId`，登记子会话引用及角色 | 重复触发按运行与会话引用去重 |
| 一轮结束 | 保存进度及已经观察到的产物和检查 | 一轮结束仅记录进度，执行可以继续 |
| 受管进程退出 | 运行器调用结算入口，写回执、释放领取并按结果推进 | 退出通知按 `runId` 幂等，进程强杀或宿主离线时靠续租失效和恢复检查 |
| `after_finish` | 处理当前会话解绑 | `task.py finish` 只代表解绑 |
| CI 完成或 PR 合并 | 后续接入事件，触发查询并回填可信交付证据 | 首版由用户触发交付核对。事件回调复核仓库、候选版本与目标分支，重复通知不重复关闭 |

各宿主 Hook 负责传递身份与事件。状态判定、并发校验和持久化集中在可直接调用的协议入口，受管运行器可以在宿主缺少退出 Hook 时完成本地闭环。

## 6. 实施及验收

| 顺序 | 实施内容 | 完成证据 |
| --- | --- | --- |
| 1 | 统一 owner 寻址、定义回执 Schema、实现领取与恢复写入层 | 两个独立进程可各领一项任务。竞争同一任务时仅一个成功。旧运行回收后无权续租或结算 |
| 2 | 接入启动器、独立 worktree、会话绑定、退出回填 | A 和 B 同时修改同一相对路径且互不覆盖。结束 A 后 B 继续运行。两者始终写入同一个任务存储 |
| 3 | 加入审查与交付门禁、原地关闭和可恢复资源回收 | 必跑验证未齐、PR 尚未合并或批准后候选变了均不能关闭。确认落地后保留审查及交付证据，关闭任务并可查询 |
| 4 | 对齐发行模板和协议文档，执行兼容与中断测试 | Windows 与 POSIX 各验证一次正常、失败、强杀、回执已写及状态已写等恢复场景。旧任务仍可读、手动完成和查看归档 |

最终演示用两个真实进程及两个 worktree。A 实现后退出，B 继续运行。第三个会话从回执审查 A，确认交付并关闭。另演示 A 中断、租约回收、旧结果拒绝及安全重领。检查运行时记录未进入 Git 跟踪。验证入口与分步回退详见 [实施拆解](implement.md)。

## 7. Vercel Board 与回退边界

首版使用仓库内脚本，不引入 Vercel 服务。Vercel Board 的租约、依赖和版本化消息作为设计参考，Vibe Kanban 的 Workspace、Session 和执行拆分作为工作区参考。实际出现跨机器共享队列需求时，再评估把 Board 作为该队列唯一的领取仲裁者，用版本化事件同步回执。MemeRig 仍以仓库内任务记录决定最终验收。 [Board 任务语义](https://vercel.com/docs/board/concepts/tasks) · [Vibe Kanban 数据模型](https://github.com/BloopAI/vibe-kanban/tree/main/crates/db/src/models)

受管入口按显式方式启用。回退时先停止新领取，核对在途执行，完成结算或安全回收后恢复手工流程。保留任务文件、回执和有未交付改动的 worktree。
