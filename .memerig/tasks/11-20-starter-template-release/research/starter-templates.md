# MemeRig 初始模板草案

## 安装边界

`blank` 安装仓库内运行所需的公共脚本和最小项目配置。它不生成项目规范、示例任务、个人记录或平台 hooks。三套可选模板以规范文件的形式覆盖到 `.memerig/spec/`。提交安装结果后，协作者可以直接使用，模板升级作为普通 Git 变更评审。

## `learn-harness` 的 `index.md`

# Learning Harness

### 开始一轮学习

1. 在任务正文写清本轮学习目标，以及能证明掌握的一个练习、作品或解释。
2. 选择一个可验证的小目标，先尝试解答或完成练习，再对照参考材料。把关键材料及其适用前提记在任务正文。
3. 说明接手者如何重现结果，例如运行练习命令、用样例输入比对输出，或独立完成同类题目。

### 保存进展

获得验证证据时，在任务正文记录「做了什么」「证据」「下一步」。只在证据满足目标后关闭任务。未完成的目标保持原状态，后续按任务 ID 接续。任务记录承担学习目标清单和完成状态，避免额外维护会话清单。

来源：[Learn Harness Engineering 的模板指南](https://github.com/walkinglabs/learn-harness-engineering/blob/main/docs/en/resources/templates/index.md)中的目标清单、证据和交接实践。

## `trellis` 的 `index.md`

# Trellis 项目规范

### 为变更定位规范

按改动所在层阅读项目的前端、后端或共享规范。维护者可以按项目现状添加 `frontend/` 或 `backend/` 规范。新规则描述仓库实际采用的目录、命令和约束。

### 在边界上定义契约

跨层变更先画出数据从输入到持久化或呈现的路径。为每个边界说明输入、输出、错误和验证责任。把序列化及校验留在契约的所有者处，避免调用方各自推断字段。

### 复用和验证

写新逻辑前检查已有实现和调用方。变化涉及共享契约时，用最接近真实调用方的路径验证正常数据、错误输入及往返结果。把新发现的可复用约定沉淀到相应层的规范。

来源：[MemeRig 分叉时的 Trellis 原始 spec 模板](https://github.com/mindfold-ai/Trellis/tree/f089cb3286071199e84118dee86b6d76aab032f1/packages/cli/src/templates/markdown/spec)中的分层规范、跨层契约、复用指南。将上游文件收录到正式发布物时，保留对应署名和许可证信息。

## `game-dev` 的 `index.md`

# Game Development

### 玩法迭代

在任务中记录玩家行为、预期反馈和可操作的验收场景。每轮验证从明确的关卡、存档或测试场景开始。记录引擎版本、目标平台、操作步骤、观察结果和已知限制。

### 资产变更

为新增资产保留原始来源、授权和导入设置。修改资源引用时，在消费该资源的场景或构建中验证加载与呈现。引擎和项目专用的命名、目录及打包规则由仓库维护者补充。

### 交付证据

提交可运行构建、可重现的测试场景或足以定位行为的试玩记录。关闭任务前确认目标玩法从启动到结果可连续执行，并记录关键的输入、画面、声音或性能反馈。

来源状态：这份是可评审的引擎无关起稿。尚未找到需求里指的 Game Dev 原模板，正式收录前先用原件校对场景、资产及验证约定。

## 发布与采用

1. 把上述规范拆到 `marketplace/specs/<id>/`。每套含 `README.md` 和规范入口 `index.md`，后续只在需要时增加主题文件。`blank` 在仓库基础初始化里定义。
2. 在 `marketplace/index.json` 增加 `type: "spec"` 条目。现有索引的 `path` 相对于 `marketplace/`。例如 `"path": "specs/learn-harness"`。
3. Marketplace 默认读取 `main` 的索引并从同一仓库取模板。合并目录和索引的 PR 后，可通过 Marketplace 下载。需要固定版本的团队从发布标签下载模板并把内容提交到自己的 Git 仓库。
4. 如需随 MemeRig 安装包离线提供三套模板，打包时从同一份 Marketplace 目录收录。分别验证发布物能离线取到三套模板，且 `blank` 启动路径无需联网。普通协作者使用项目里已提交的文件。
5. 带现有规范的项目先在分支上应用模板并评审差异。新项目初始化完成后，用干净克隆验证常用任务命令和规范入口。
