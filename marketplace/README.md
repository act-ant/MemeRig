# MemeRig Marketplace

Downloadable templates for MemeRig. The CLI reads `index.json` at the selected
Git revision. Each `path` is relative to the directory containing that index,
which can be the root of a standalone registry repository.

## Structure

```
marketplace/
├── index.json            # Template registry (ids, types, names, relative paths)
├── skills/               # Claude Skills (.claude/skills/)
├── specs/                # Spec templates (.memerig/spec/)
├── rules/                # Optional rule declarations (manual adoption; not registry entries)
└── workflows/            # Workflow templates (.memerig/workflow.md)
```

## Optional rule catalog

[`rules/`](./rules/README.md) contains optional, reusable rule declarations for clean
cutover, production compatibility, dependency governance, and architecture research.
They are reference documents, not active project instructions, and they are not
registered in `index.json` or copied by `memerig init` / `memerig update`. There is no
installer flag or rule registry.

Read the catalog in [English](./rules/README.md) or [简体中文](./rules/README_CN.md) for
the Rules/Spec boundary, pinned manual adoption, task-context wiring, and removal/upgrade
handling. The default `.memerig/rules/index.md` and `core.md` are delivered by the normal
project template, separately from this optional catalog.

## Starter spec presets

These presets are safe defaults for a new project. They only add project specs; the
`blank` initialization stays free of project-specific rules, example tasks, personal
records, and platform hooks.

| Id | Use when | Entry point |
|----|----------|-------------|
| [`learn-harness`](./specs/learn-harness/index.md) | The repository is for learning, exercises, or deliberate practice | Goal → attempt → evidence → handoff |
| [`trellis`](./specs/trellis/index.md) | Conventions differ by frontend, backend, or shared layer | Layer routing, boundary contracts, reuse checks |
| [`game-dev`](./specs/game-dev/index.md) | Work is judged by a playable build, scene, or prototype | Playable scenarios, asset provenance, playtest evidence |

Each preset directory contains:

- `README.md` — purpose, adoption steps, and source attribution.
- `index.md` — the spec entry point installed into `.memerig/spec/`.

All three are distributed in two places with identical bytes:

1. **Marketplace source** — `marketplace/specs/<id>/`, served from the selected Git ref.
2. **Release artifact** — `packages/cli/dist/templates/starter-specs/<id>/`, generated by
   `packages/cli/scripts/copy-templates.js` during `pnpm --filter memerig build`.

The CLI resolves the release copy through `getBuiltinSpecDirectory(id)` in
`packages/cli/src/utils/builtin-specs.ts`. `BUILTIN_SPEC_IDS` is the exported id list used
by installer help and validation. An installed CLI therefore needs no network access for
these presets. The default blank initialization installs no spec files at all.

Reusable platform assets such as built-in skills and hooks live in the private
workspace package `packages/templates/assets/`. The CLI ships those assets
alongside the bundled starter specs in its npm tarball.

## Install and adopt

### From a release artifact (offline)

1. Install the MemeRig release through your normal distribution channel and run
   `memerig init` in the project.
2. Pass the preset id explicitly:

   ```bash
   memerig init --template learn-harness   # or trellis / game-dev
   ```

   The installer copies the bundled directory into `.memerig/spec/`; no download is
   attempted. Omitting `--template` keeps the blank initialization, which installs no
   project spec and no onboarding task.
3. Review and commit the installed files. Keep `README.md` next to `index.md` so the
   attribution stays in the project.

For an existing project, apply the preset on a branch and review `git diff` before
committing. The installer must preserve files you edited and report conflicts rather than
silently overwriting them. If your release does not offer the preset selector yet, use one
of the pinned/manual paths below.

### Install from a standalone registry

For a copyable repository with examples and GitHub Actions validation, use the
[standalone marketplace starter](./starter/README.md).

Put `index.json`, `specs/`, and `workflows/` in your registry repository and
publish a Git tag. For a registry with the spec `team-spec` and workflow
`team-flow`, run these commands from the target project:
```bash
memerig init --template team-spec --registry gh:myorg/memerig-marketplace#v1.0.0
memerig workflow --template team-flow --marketplace gh:myorg/memerig-marketplace#v1.0.0
```

Set each spec entry's `path` to its directory and each workflow entry's `path`
to its `workflow.md`. A registry can keep its own release cadence.

### Pin a Git revision

Marketplace defaults to `main`, which is suitable for trying a preset but not for a
repeatable project setup. Pin a release tag or a full commit SHA:

```bash
git clone https://github.com/blackplume233/MemeRig.git /tmp/memerig
git -C /tmp/memerig checkout <release-tag-or-commit>
mkdir -p .memerig/spec
cp -R /tmp/memerig/marketplace/specs/learn-harness/. .memerig/spec/
git add .memerig/spec
git diff --cached -- .memerig/spec
```

Replace `learn-harness` with `trellis` or `game-dev`. Copy only files that do not already
exist when preserving local edits, or merge the diff explicitly. Keep the adopted commit
recorded in the project (for example in the pull request or a spec note) so an upgrade can
compare against the exact previous revision.

On PowerShell, use `Copy-Item -Recurse` for the copy step:

```powershell
Copy-Item -Recurse C:\temp\memerig\marketplace\specs\learn-harness\* .memerig\spec\
```

### Manual copy (no MemeRig CLI)

The presets are plain Markdown. A collaborator can adopt them with only Git:

```bash
git clone https://github.com/blackplume233/MemeRig.git /tmp/memerig
git -C /tmp/memerig checkout <release-tag-or-commit>
mkdir -p .memerig/spec
cp -R /tmp/memerig/marketplace/specs/trellis/. .memerig/spec/
```

Commit `.memerig/spec/` with the project. Collaborators then receive the adopted template
through ordinary Git review; they do not need the Marketplace or the MemeRig npm CLI.
Upgrading means repeating the copy from a newer pinned revision and reviewing the
resulting diff.

## Publish or update a spec preset

1. Add or update the canonical files under `marketplace/specs/<id>/`. Include
   `README.md` (purpose, adoption, attribution) and `index.md` (the spec entry point).
   Keep relative links valid from the installed `.memerig/spec/` location.
2. Add one entry to `marketplace/index.json`:

   ```json
   {
     "id": "learn-harness",
     "type": "spec",
     "name": "Learning Harness",
     "description": "Goal-and-evidence learning workflow with reproducible handoffs",
     "path": "specs/learn-harness",
     "tags": ["learning", "education", "evidence", "handoff"]
   }
   ```

   `path` is relative to `marketplace/`, so a spec directory is `specs/<id>` — never an
   absolute path or a repository-root path.
3. To ship an official spec offline, set `"bundled": true` on its index entry.
   The CLI build copies the spec from `specs/<id>/` and includes the index in
   the tarball. Installer help reads the bundled IDs from that index.
4. Verify that every `type: "spec"` entry resolves to a real directory, and that the
   bundled starter presets have their `index.md` entry point:

   ```bash
   jq -r '.templates[] | select(.type == "spec") | .path' marketplace/index.json |
     while read -r p; do test -d "marketplace/$p" || echo "missing: $p"; done
   for id in learn-harness trellis game-dev; do
     test -f "marketplace/specs/$id/index.md" || echo "missing index: $id"
   done
   ```

5. Build the package and confirm the bundled bytes match the Marketplace source:

   ```bash
   pnpm --filter memerig build
   diff -r marketplace/specs/learn-harness \
     packages/cli/dist/templates/starter-specs/learn-harness
   ```

   On Windows:

   ```bash
   git diff --no-index -- marketplace/specs/learn-harness \
     packages/cli/dist/templates/starter-specs/learn-harness
   ```

6. Land the change through the normal pull-request and release process. Marketplace
   serves `main`; a release tag or commit SHA is the stable adoption point. Do not edit
   `packages/cli/dist/` by hand and do not publish packages locally — CI owns npm
   publication.

An upgrade is a normal reviewed change: issue a new commit or release, then update the
adopted copy in the consuming project and review the diff. Existing project edits take
precedence unless the maintainer explicitly accepts the upstream change.
