# MemeRig Meta

This skill is for local MemeRig users who have already run `memerig init` in a project. After reading it, an AI should understand the MemeRig architecture, operating model, and customization entry points inside that user project, then modify the generated `.memerig/` and platform directory files according to the user's request.

MemeRig v0.6 adds three architectural surfaces on top of the pre-v0.6 workflow / persistence / platform model. First, a multi-agent collaboration runtime: `memerig channel` coordinates multiple AI worker processes through project-scoped JSONL event logs at `~/.memerig/channels/<project>/<channel>/events.jsonl`, with worker OOM guard, forum/thread channels, durable idempotency keys, and bundled `.memerig/agents/{check,implement}.md` runtime definitions. Second, cross-session memory: `memerig mem list | search | context | extract | projects` reads raw Claude Code, Codex, and Pi Agent JSONL already on disk, slices by `--phase brainstorm|implement|all`, and never uploads anything. Third, a dual-package npm release: `memerig` (CLI) and `memerig-core` (SDK with `/channel`, `/task`, `/mem`, `/testing` subpaths) ship in lockstep on one version. Treat these as first-class customization surfaces alongside the per-platform integration files.

The default operating scope is local files in the user project:

- `.memerig/`: workflow, config, tasks, spec, workspace, scripts, bundled runtime agents, and runtime state.
- Platform directories: `.claude/`, `.codex/`, `.cursor/`, `.opencode/`, `.kiro/`, `.gemini/`, `.qoder/`, `.codebuddy/`, `.github/`, `.factory/`, `.pi/`, `.reasonix/`, `.kilocode/`, `.agent/`, `.devin/`, `.kimi-code/`, and similar directories. Pi additionally exposes a native `memerig_subagent` tool with `single` / `parallel` / `chain` dispatch modes, throttled progress cards, and `isMemerigAgent()` validation on top of the file layout. Reasonix stores both workflow skills and subagent skills as `.reasonix/skills/<name>/SKILL.md`; subagent skills carry `runAs: subagent` frontmatter. Kimi Code keeps workflow skills in the shared `.agents/skills/` layer, delivers commands plus agent prompts as `.kimi-code/skills/<name>/SKILL.md`, and installs the same agent prompts as custom sub-agents under `.kimi-code/agents/<name>.md`.
- Shared skill layer: `.agents/skills/`.
- User-owned channel store outside the project tree: `~/.memerig/channels/<project>/<channel>/events.jsonl`.
- Raw platform conversation logs queryable via `memerig mem`: `~/.claude/projects/`, `~/.codex/sessions/`, and `~/.pi/agent/sessions/` (OpenCode adapter degraded for the v0.6 line).

Do not assume the user has the MemeRig source repository. Do not default to modifying the global npm install directory or `node_modules` — both `memerig` and `memerig-core` ship as published packages sharing one version and one git tag per release.

## How To Use

1. Read `references/local-architecture/overview.md` first to establish the local MemeRig system model.
2. If the request involves a specific AI tool, read `references/platform-files/platform-map.md` and the relevant platform file notes.
3. If the request involves multi-agent dispatch or channel workers, read `references/local-architecture/multi-agent-channel.md` and the bundled `.memerig/agents/` files.
4. If the user wants to change behavior, read `references/customize-local/overview.md`, then open the specific customization topic.
5. Before editing, read the actual files in the user project and treat local content as authoritative.

## Current Rules

- `.memerig/workflow.md` is the local workflow source of truth; its initial content was selected from a workflow template (built-in `native`, `tdd`, `channel-driven-subagent-dispatch`, or a marketplace template) at `memerig init` time and can be re-selected via `memerig workflow --template <id>`. Missing `.memerig/agents/<name>.md` files referenced by the active template trigger a non-blocking stderr warning pointing at `memerig update`.
- `.memerig/config.yaml` is the project-level MemeRig configuration entry point. It hosts task lifecycle hooks (`hooks.after_create` / `after_start` / `after_finish` / `after_archive`), journal shape (`session_commit_message` / `max_journal_lines` / `session_auto_commit`), channel worker guard (`channel.worker_guard.idle_timeout` / `max_live_workers`), Codex dispatch mode (`codex.dispatch_mode: inline | sub-agent`), and the spec registry block (`registry.spec.source` + `registry.spec.template`).
- `.memerig/spec/` stores the user's project-specific coding conventions and design constraints. When `registry.spec` is set, files are refreshed by `memerig update`; local edits surface as "modified by user" conflicts in `.memerig/.template-hashes.json`.
- `.memerig/attractor-guide.md` is the installed default method for the optional repository attractor; `.memerig/spec/attractor.md` is its user-owned output when a project adopts the practice. Only the selected template/project instructions or an explicit user request activate it. The guide file, bundled `attractor` skill, or an existing attractor is not adoption, a requirement, or a missing-file warning in silent projects.
- `.memerig/tasks/` stores task PRDs, design notes, implement plans, research files, and JSONL context. Tasks form parent/child trees: `task.py create --parent <slug>`, `task.py add-subtask <parent> <child>`, `task.py remove-subtask <parent> <child>`, and `task.py list-context <task>`. `task.py create` rejects a slug already present in `.memerig/tasks/archive/**`.
- `.memerig/workspace/` stores **deliberately written** developer journals. Raw cross-session dialogue is **not** stored here — it lives on disk under `~/.claude/projects/`, `~/.codex/sessions/`, and `~/.pi/agent/sessions/` and is recovered via `memerig mem search|extract|context`. The bundled `session-insight` skill teaches when to reach for `mem`.
- `.memerig/agents/{check,implement}.md` are bundled, platform-agnostic channel runtime agent definitions loaded by `memerig channel spawn --agent <name>`. Editable; `memerig update` backfills missing ones. Editing the per-platform `memerig-implement.md` / `memerig-check.md` does **not** change channel-runtime worker behavior.
- `~/.memerig/channels/<project>/<channel>/events.jsonl` is the channel runtime event log per project per channel. User-owned, file-locked sequence numbering, durable `idempotencyKey` support; never under `.memerig/`.
- Bundled multi-file skills (`meta`, `spec-bootstrap`, `session-insight`, `channel`, `attractor`) are auto-dispatched to every platform skill root by `getBundledSkillTemplates()` in `packages/cli/src/templates/common/index.ts`. Dropping a new directory under `packages/templates/assets/common/bundled-skills/` (upstream) ships it to every platform on the next `memerig update`.
- Platform settings/config files decide which hooks, agents, skills, commands, prompts, and workflows actually run. Reasonix has no settings file — behavior is encoded inside skill frontmatter.
- `.memerig/.template-hashes.json` and `.memerig/.runtime/` are management/runtime state files. Confirm necessity before editing them.

## Do Not

- Do not treat MemeRig upstream source code as the default target for local customization.
- Do not modify the global npm install directory or `node_modules/memerig` or `node_modules/memerig-core` to implement project needs; both packages ship in lockstep.
- Do not overwrite user-modified local files with default templates; check `.memerig/.template-hashes.json` first and prefer `.new` sidecar files over destructive overwrites.
- Do not put team-private project rules into any public bundled skill (`meta`, `spec-bootstrap`, `session-insight`, `channel`, `attractor`); put project rules in `.memerig/spec/`, a project-local skill, the current task, or the workspace journal — `memerig update` will overwrite anything inside a bundled skill directory.
- Do not introduce attractor questions, mandatory files, context injection, or completion gates into a project whose selected template has not adopted the practice.
- Do not hand-edit `~/.memerig/channels/<project>/<channel>/events.jsonl`; sequence numbers are assigned under a file lock and replay-safe writes go through the `memerig channel` CLI or the `memerig-core/channel` SDK.
- Do not edit `.claude/agents/memerig-implement.md` (or any other per-platform sub-agent file) when the goal is to change channel runtime worker behavior — edit `.memerig/agents/<name>.md` instead.
- Do not describe removed or never-shipped mechanisms as current MemeRig behavior; cross-check against the local `.memerig/config.yaml` and the installed CLI's `memerig --help` before claiming a knob exists.
