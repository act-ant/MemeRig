# MemeRig

**An agent harness for game and agent development.** MemeRig keeps specs, tasks, and session memory in your repository, so every coding agent starts each session with the same conventions and picks up where the last one stopped.

## What changed from Trellis

| Area | Trellis | MemeRig |
| --- | --- | --- |
| Project directory | `.trellis/` | `.memerig/` |
| CLI | `trellis`, `tl` | `memerig`, `mrig` |
| npm packages | `@mindfoldhq/trellis`, `@mindfoldhq/trellis-core` | `memerig`, `memerig-core` |
| Skills | `trellis-brainstorm`, `trellis-check`, … | `brainstorm`, `check`, … (no prefix) |
| Sub-agents | `trellis-implement`, `trellis-check`, `trellis-research` | `memerig-implement`, `memerig-check`, `memerig-research` |
| Slash commands | `/trellis:start`, `/trellis:finish-work` | `/memerig:start`, `/memerig:finish-work` |
| Environment variables | `TRELLIS_*` | `MEMERIG_*` |
| Template marketplace | `mindfold-ai/marketplace` submodule | vendored in [`marketplace/`](./marketplace) |

Sub-agents keep a prefix because the main session dispatches them by name, and generic names such as `check` or `implement` collide with agents that projects define themselves.

## Requirements

- Node.js 18.17 or newer
- Python 3.9 or newer

## Quick start

```bash
# Install the CLI
npm install -g memerig

# Initialize a repository
memerig init -u your-name

# Or initialize only the platforms you use
memerig init --claude --codex --omp -u your-name
```

`memerig init` creates `.memerig/` plus the platform files for each agent you select. Run `memerig platforms` to list every supported host.

## How it works

MemeRig runs each task through four phases:

1. **Plan.** The `brainstorm` skill works through requirements one question at a time and writes `prd.md`. Complex tasks also get `design.md` and `implement.md`.
2. **Implement.** The `memerig-implement` sub-agent writes code from the PRD, with the relevant specs injected into its context.
3. **Check.** The `memerig-check` sub-agent reviews the diff against the specs and runs lint, type checks, and tests.
4. **Finish.** `/memerig:finish-work` completes the task in place and records the session journal. The `update-spec` skill writes new lessons back into `.memerig/spec/`.

| Path | Holds |
| --- | --- |
| `.memerig/spec/` | Coding conventions, scoped by package and layer |
| `.memerig/tasks/` | Task PRDs, designs, research, and context manifests |
| `.memerig/workspace/` | Per-developer session journals |
| `.memerig/workflow.md` | Phase definitions and the per-turn workflow-state prompts |
| `.agents/skills/` | Skills shared across hosts that follow the agentskills.io layout |

## Developing MemeRig

MemeRig is developed with MemeRig: the repository's own `.memerig/`, `.claude/`, `.cursor/`, `.opencode/`, `.codex/`, `.pi/`, and `.agents/skills/` files are generated by the CLI from `packages/templates/assets/`.

```bash
pnpm install
pnpm build
pnpm test
```

After editing the contents of an existing template, run both commands from the repository root:

```bash
pnpm sync:templates
pnpm update:self
```

`sync:templates` copies assets into `packages/cli/dist/` without compiling TypeScript. `update:self` uses the local CLI and renders Python commands for the host (`python` on Windows, `python3` elsewhere). It honors `MEMERIG_PYTHON_CMD` when set. Use `pnpm update:self --dry-run` to preview the changes and keep the repository's `.memerig/config.yaml` when prompted.

On a fresh checkout, after a TypeScript change, or after deleting or renaming a template, run `pnpm build` before `pnpm update:self`.

Hook and workflow changes affect the agent session you are working in, so try them in a scratch project (`memerig init` in a temp directory) before relying on them here.

To use this checkout's CLI anywhere on your machine, link it globally:

```bash
pnpm install:global
```

That builds `packages/cli` and then runs `npm link` inside it, so `memerig` and `mrig` on PATH resolve to this repository. A plain global install cannot work from here: `packages/cli` depends on `memerig-core: workspace:*`, which only resolves inside the workspace. Re-run it after a rebuild if you ever replace the symlink, and never run `memerig upgrade` while linked — it installs the registry package over the symlink.

## CI and releases

GitLab (`platgit.mihoyo.com`) is the release upstream: branches and tags land there first. GitHub stays a mirror — `.github/workflows/ci.yml` and `publish.yml` still run the same gates there, and `.gitlab-ci.yml` carries the primary pipeline. The gate order is duplicated on purpose; change both files together.

| Trigger | GitLab (`.gitlab-ci.yml`) | GitHub (`.github/workflows/`) |
| --- | --- | --- |
| Push to `main`, merge request | `python-3.9-syntax`, `test` | `CI` |
| Tag `v*` | `test`, then `publish` | `Publish to npm` |

Publish prerequisites on the GitLab project:

- `v*` tags marked **Protected** — protected CI/CD variables are only exposed to protected refs.
- `NPM_TOKEN` CI/CD variable, **masked** and **protected**. npm's trusted publishing covers GitLab.com shared runners only, so a self-hosted instance authenticates with this token.
- Runners able to pull `node:24` and `python:3.9`, or point `NODE_IMAGE` (and the Python job's image) at internal mirrors.

Cutting a release:

```bash
pnpm release        # or release:minor / release:major / release:beta / release:rc
```

The release script runs the pre-release gates, bumps both packages, commits `chore(release): <version>`, tags `v<version>`, and pushes the branch plus tags to `origin`. The tag pipeline then publishes. Re-running a tag pipeline is safe: `release-preflight` skips any package version already on npm.
